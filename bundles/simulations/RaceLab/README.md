# RaceLab 0.15.1 · SoftN race simulator

Import `RaceLab.softn` into SoftN Builder or a compatible web/desktop host. This archive contains the editable `.ui` / `.logic`, local XDB schema, documentation, the historical input dataset at `assets/historical-cups.json` and the attributed research sidecar at `assets/cup2026-research.json`. Market prices are not bundled. It uses SoftN's Three.js-backed Scene3D and Loop. Once the host and its 3D dependencies are available, the app itself requires no network service.

## Website hosting assets

The accompanying `RaceLab-Hosting.zip` is updated for version 0.15.1 and provides `data/apps/racelab/app.json`, `app.softn`, `thumb.png` and `icon.svg` for the SoftN website folder catalogue. The catalogue metadata explicitly references the two sibling image files. This bundle also declares the same icon at `assets/icon.svg`, so importing the bundle independently retains the icon. The thumbnail is illustrative cover artwork, not a screenshot or surveyed view of the course.

For a new listing, copy the supplied `racelab` folder into the website API's `data/apps/` directory. SoftN discovers it on the next API request. Keep only one copy of this bundle in that folder. For subsequent updates, preserve the server-managed `app.json` and change only the intended metadata fields; it may contain comments, ratings and derived version data. Upload the bundle with a temporary extension and rename it to `.softn` when complete.

## Simple and Advanced modes

**Simple** is the default on phones and desktops. Choose the going scenario and simulation count, press **Run & watch**, and watch a freshly sampled race after the simulation batch completes. A single action bar provides **Run & watch**, **Play/Pause/Replay** and **Skip to result**, with status and progress in one place. The one-column view contains the race, its complete finishing order, five leading model chances, a compact boxed-trifecta search and an optional folded ticket selector. Drag the scene to rotate; **− / +** and **Reset view** handle basic framing. The experimental-model notice and a compact, expandable data-freshness summary remain visible. If Portfolio mode is active, a short portfolio summary replaces the quick-box selector. One compact audit card reports market/research status without exposing the Advanced controls.

**Advanced** reveals history/barrier/pace assumptions, saved scenarios, full forecasts, evidence and historical checks, field editing, JSON import/export, replay codes, playback speed, camera presets, extra camera controls, horse detail, replay timeline/focus, Portfolio Lab, model/research settings and the folded market/research audit workspace. Switching modes changes presentation only: it preserves the current settings, imported field, batch, replay and playback state. A brief retained-settings summary appears in Simple when Advanced choices differ from the defaults. Simple uses rotating drags while retaining the Advanced drag-mode preference for the next switch back.

## Race controls

- **Run & watch** starts a fresh simulation batch and automatically plays its first sampled race. **Analyze without playback**, in Advanced, calculates a fresh batch without autoplay. The shared **Simulations** selector offers 1,000, 5,000, 20,000 or **100,000** trials in both modes. The default remains 5,000. Changing the count invalidates old box suggestions and does not itself draw a new race. Work proceeds in chunks of up to 1,000 trials, then finalisation and four optional assumption-comparison stages. The progress counter may reach its target while those comparisons finish. There is no seed input in the normal workflow. Two fresh batches can still share a winner.
- **Save this replay code** appears in the Advanced output details. The full RL11 code captures the internal random seed, raw field, accepted snapshot ID, research snapshot ID, model identity/settings, ticket or portfolio, hypothetical dividend scenario, track and data versions. Copy the complete code, then paste it into **Reproduce a race** to restore the same batch outcomes in compatible releases, including v0.14 and later releases that retain the same model, track and replay-data versions. Compatible older RL11, RL9, RL8 and RL7 codes are accepted when their required model, track and data versions are available. A run ID alone is insufficient after settings change. New RL11 codes require track version 0.7 and compatible model, data and research snapshots. Compatible RL9 / track 0.7, RL8 / track 0.6 and RL7 / track 0.5 codes are also accepted and restore the original baseline model settings: batch counts, finishing order and finish timing are preserved while the horses use the updated artwork. A compatibility note is shown and included in the export; older artwork is not reproduced pixel for pixel. Earlier RL5/RL6 payloads require their original app. Invalid, incomplete or incompatible codes are rejected before changing the current scenario. Because replay payloads are editable, restored horse data is marked imported and unverified. That provenance normalisation may change the code bytes, while the restored batch outcomes remain reproducible with compatible model, track and data versions.
- **Play / Pause** watches or pauses the first sampled race from the batch. After completion, Play replays the same result. **Restart sample**, in Advanced, returns that sample to the gates and cancels queued autoplay if analysis is still running. While a batch is running, **Play when ready** queues playback; **Cancel play** clears that queue.
- **Skip to result** goes straight to the complete result of that same sample. If no current sample exists, it calculates one first. For unchanged race inputs it uses the current sample. Changing the field or race assumptions requires a new batch; changing only the ticket preserves the sampled race.
- **1× / 4× / 12×**, in Advanced, change playback speed, not horse performance. The clock is simulated time. The leading-order strip pins runners to their sampled finishing order after crossing the line and shows the final order when all have finished; post-finish run-out does not silently reorder the result. Default 4× is roughly a minute of simulated playback; the host can affect wall-clock timing. Every runner accelerates from rest, travels with smooth individual pace variation and crosses the finish. Each runner then decelerates through its own 12-second run-out, with its stride and body motion settling to rest. Hoof placement is aligned to the turf rather than floating below it. Finish gaps are varied and seeded, with a longer tail rather than fixed 0.11s spacing.
- The Advanced presets **Broadcast**, **Follow** and **Overhead** select the view. **Broadcast** tracks the moving field; **Follow** tracks its leader or the active runner selected in **Replay timeline & horse focus**; **Overhead** shows the course. Camera rotation, tilt, zoom and pan remain available while the race runs and preserve their offsets as the chosen view follows the field. Selecting a preset or **Reset view** restores its default framing. **Text view** retains timing, live order and results while skipping horse-mesh construction and removing the 3D view. Switching back reconstructs the current visual state; it does not resample the race. The app also avoids synchronising duplicate horse-mesh descriptors in both the scene state and objects list. More than 24 active runners automatically use the text fallback to bound scene load; the statistical forecast still supports up to 40 horses. A fallback explanation remains visible.
- The Advanced **Rotate / Pan / Zoom** controls select what a mouse or single-finger drag does on the scene. In Zoom mode, drag up to move closer and down to move farther away. The **− / +** buttons and expandable **Turn, tilt & move the camera** controls provide the same adjustments with 44 px targets. With the scene focused, arrows turn or tilt, Shift + arrows pan, **+ / −** zoom, and **0** or **Home** reset the view. Tab and modified browser shortcuts remain available. The mouse wheel scrolls the page normally; pinch zoom is not implemented. Leaving the scene or ending a touch stops the drag.
- **Horse detail**, in Advanced, offers **Balanced · lighter** (the default) and **Detailed**. Balanced retains the rounded horse anatomy, articulated legs and crouched rider while omitting small decorative parts and limiting the scene pixel ratio to 1. Detailed adds finer jockey, tack and hoof details and permits a pixel ratio up to 1.5. The setting changes presentation only: probabilities, race paths and finish times are identical. It is a viewing preference rather than a statistical or replay input, so restoring a replay keeps the currently selected quality. Results JSON records the current view as `sampledAnimation.visualQuality`.
- **Replay timeline & horse focus**, in Advanced, seeks through the existing sample and pauses at the selected time. Chapters jump to 2,400 / 1,600 / 800 / 400 metres remaining or the winner crossing the finish; the slider also covers the remaining runners and run-out. Seeking does not generate a new race. The selected horse affects the Follow camera; a missing or scratched selection falls back to the leader. A small SVG course map shows illustrative runner positions. **Scene updates** offers 33 / 66 / 100 ms intervals, approximately 30 / 15 / 10 updates per second; 66 ms is the default. These are update requests, not measured rendered FPS.
- The aggregate results appear when the batch completes. The animated race’s result card remains hidden until completion or Skip, then shows all active runners and, if a complete box was selected, whether it covered the sampled first three. In Portfolio mode it reports the number of winning tickets and, only if supplied, the hypothetical settlement. Margins/times are illustrative animation values.

Batch processing tracks its stage and completed-trial count independently of rendered control state. A lightweight periodic lifecycle check restores batch/search running flags from private job state, including the initial batch, so a delayed mobile UI update cannot leave the job stalled. This is a state-recovery safeguard, not a measured phone-performance claim. Delayed UI updates therefore cannot repeat a finished stage or add trials beyond the requested count. If the optional history/barrier comparison fails, the completed simulation and sampled race remain available with a short notice in both modes. The export records the comparison status and failure reason, and leaves its unavailable report null rather than substituting results.

## Field, tickets and local saves

The numerical field/barrier/weight snapshot is dated **31 October 2026**. The separately dated 3 November field and history overlays update displayed trainer/jockey information, reviewed history and the checked scratching status; check subsequent changes independently. A ticket is optional: leave the selection empty or select one or two runners to explore the full-field batch analysis and watch races without a complete box. Select at least three distinct active saddlecloth numbers by tapping field cards or entering comma-separated numbers to evaluate a boxed trifecta. A box of n horses covers n(n−1)(n−2) ordered combinations; flexi share assumes a $1 unit. Changing only ticket selections or stake preserves the current sampled race and updates its ticket result. No actual dividend is known. Portfolio mode can evaluate an explicitly hypothetical dividend scenario; those figures are not expected real-world returns.

Each profile in Advanced has a separate **Scratch runner / Reinstate runner** control. A scratch leaves the profile available for reinstatement, compacts the active gates, removes that runner from the ticket and clears the old batch, replay and exported output. A new batch is required for the changed field. The action validates the complete candidate field before committing and will not reduce it below three active runners. A reinstated runner is not silently added back to a ticket.

The advanced editor accepts one runner per row:

`saddlecloth,name,drawn barrier,strength,active,weight,stamina,wet preference,style`

Strength is positive, active is 1 or 0, stamina/wet range from −1 to 1, and style is `front`, `mid` or `close`. Set active to 0 to scratch. The original drawn barrier is retained; actual gates compact inward in drawn-barrier order, matching the VRC-described scratching rule. Both original draw and effective gate are displayed. Apply field updates the field; Analyze without playback applies it and calculates. Changes to field or race assumptions invalidate the current estimate. Edited fields are labelled accordingly; renamed runners do not inherit another horse's form evidence. Save settings / Load settings keeps one scenario in app-local XDB, including horse evidence and the settings. Loading validates the complete field, selections and scenario before committing any changes; a malformed saved scenario leaves the current scenario intact. User-edited fields retain their edited origin instead of being labelled as the official snapshot. Imported and restored payloads do not gain verified-source status from their own provenance claims. Results may change across future model versions. Save before updating the application.

When complete surface counts reconcile, the runner evidence view and results JSON show observed turf and synthetic career totals separately. These are descriptive aggregates only: they do not add a surface-specific model coefficient, and imported history may include jumps or unknown surface categories. Missing or inconsistent records are marked unavailable rather than treated as evidence of suitability.

## Top boxed-trifecta search

Choose **3–10 horses per box** and **1–25 boxes**, then press **Rank boxes from this batch**. When no current batch exists, **Run batch & rank boxes** starts one first. The search runs in chunks and can be cancelled. Simple displays the first three individual results; Advanced shows up to ten and provides a candidate-list control. Both modes provide **Copy box numbers** and a read-only, numbers-only preview of all generated tickets, one comma-separated box per line. If clipboard access is unavailable, select the preview manually. Detailed analysis and JSON result exports remain available.

With **three horses per box** and an empty candidate list, the app searches every combination of active runners and ranks them by their exact Plackett–Luce model probability; sampled hits are a separate diagnostic. A user-specified list limits the search to 3–12 active candidates. Distinct three-horse boxes cannot overlap in the ordered results they cover, so choosing the highest exact probabilities maximizes coverage within the selected pool *under the model*. Ties use saddlecloth numbers. The exact probabilities remain conditional on the model and are not calibrated real-race probabilities or evidence of betting value.

For **four–ten horses per box**, the default candidate pool remains at most 12 runners selected by sampled top-three frequency; a custom pool also has at most 12. Boxes are ranked by sampled coverage within that pool, while exact model coverage is shown separately. The incremental-coverage list uses a greedy sampled-coverage method: it counts overlap once, but its chosen set is not guaranteed globally optimal. Every active runner still remains in the race probability denominator. Results selected using the batch have no selection-adjusted uncertainty interval.

A box with N horses covers `N × (N−1) × (N−2)` ordered trifectas: 3 cover 6; 4 cover 24; 6 cover 120; 10 cover 720. Each box is a separate ticket, and overlapping ordered combinations are paid for on each ticket. For example, 25 four-horse boxes cost $600 at a $1 unit, while $150 total corresponds to 25% flexi if the bookmaker accepts the individual stakes. Actual operator pricing and minimums vary. RaceLab does not place bets or predict dividends.

**Generated box collection** provides a separate calculator for up to 25 generated boxes. Edit each ticket's total stake or apply one stake to all; the initial $1 amount is per ticket, not per ordered combination. The view displays individual combination counts and flexi shares, total stake, and the search's model and simulated union coverage. Enter an ordered first-three finish to see which boxes would cover it; optionally enter a declared $1 dividend for an illustrative gross and net settlement. It also offers a copyable detailed list and includes the current collection in the results JSON. A manual dividend is hypothetical input, not an expected payout forecast. Changing the field, going or search invalidates the collection.

In the collection, **Set 100% of $1 unit for every box** is an explicit action: it sets each ticket's total stake to its ordered-combination count in dollars. For example, each three-horse box becomes $6, so 25 boxes total $150. Nothing is placed automatically. **Review your receipt before copying** displays each ticket’s combinations, stake and percentage, plus the total; **Copy receipt** copies those details.

**Stake validation** offers **Generic research calculator** or **TAB published flexi checks**. The generic calculator accepts mathematical stakes from one cent. The optional TAB profile checks each separate ticket for the published $0.50 minimum, $0.50 increments and at least a 1% bet percentage; invalid values prevent receipt copying until corrected. The checks cannot guarantee actual acceptance: verify the [current TAB Flexi rules](https://help.tab.com.au/betting-on-racing/what-is-flexi-betting), product, channel and final betslip. Other operators can have different rules.

**Use this quick box** transfers one result to the quick-box selection without changing horse strengths. **Use these boxes as a portfolio** remains available for sets of at most six tickets, the limit of the separate Portfolio Lab's exact overlap-distribution analysis. Larger generated sets remain available in the collection view; they are never silently truncated. Ticket-only changes retain the sampled study, while changing the field, model, going, candidates, box size, box count or trials invalidates incompatible suggestions.

100,000 trials reduce Monte Carlo noise, but cannot correct unvalidated rating conversion, uncertain historical evidence or omitted racing factors. The exact three-horse ordering removes sampling noise from *selection under the model*, not uncertainty about the real race. The results JSON records the seed, field identity, candidate pool, selection strategy, exact probabilities, sampled counts and union coverage. Earlier replay codes retain their embedded field and compatible model version.

## Trifecta Portfolio Lab

Advanced contains an optional folded **Trifecta Portfolio Lab**. Switch explicitly between the quick box and a portfolio; the previous quick selection is retained. Add up to six named tickets, choose **Boxed trifecta** or **Ordered trifecta**, enter active saddlecloth numbers and a positive AUD stake with at most two decimal places. An ordered ticket requires exactly three distinct runners in first/second/third order. Each row shows its ordered combinations, flexi share of a $1 unit and exact model coverage. The whole active race field remains in the denominator.

The nested-box wizard accepts runners in priority order, comma-separated tier sizes chosen from **4 / 6 / 8 / 9 / 10**, and one matching AUD stake per tier. Each tier uses the first N runners from the same list, so the selections remain nested. It validates active runners, increasing sizes and matching stakes before replacing the portfolio.

The saved **4 / 6 / 10** example loads the supplied nested selections and $24 / $30 / $96 stakes; it replaces the portfolio rows and is not a recommendation. The smallest selection is 20, 2, 11, 12; the six adds 4 and 16; the ten adds 1, 10, 22 and 24. Those cover 24, 120 and 720 ordered combinations, with flexi shares of 100%, 25% and 13.3333% respectively. The total stake is $150. If a required runner is unavailable, validation reports the problem rather than silently replacing a selection.

Exact portfolio probabilities enumerate covered ordered first-three outcomes once. **At least one pays** is the union, with separate probabilities for exactly one, exactly two, and three or more winning tickets. In a nested portfolio, the widest box determines the union; summing the individual coverage percentages would double-count. Batch counts are a separate Monte Carlo check of the same full-field distribution. Adding, removing or editing tickets must not change the seeded race outcomes; refreshed ticket counts may require re-evaluating the batch with the same seed.

The optional **Declared dividend scenario (AUD per $1)** starts blank. **Actual dividend unknown** remains the interpretation until a hypothetical value is supplied. For each overlap case, gross payout is the supplied dividend multiplied by the sum of winning flexi shares. Net payout subtracts the entire portfolio stake, including losing tickets. The displayed hypothetical mean also assumes this same dividend for every covered outcome; it is not a forecast of dividends or expected real-world profit. **Expected monetary payout is not estimable** without the outcome-specific dividends. This remains separate from a user-supplied constant-dividend scenario, and WIN prices are never converted into invented trifecta dividends. No bookmaker or wagering integration is provided.

**Import or export portfolio JSON** uses `racelab-portfolio-settings-v1`, separate from the horse JSON. **Prepare portfolio JSON** writes the current definitions into the text area; copy it or paste a saved definition and use **Import portfolio JSON**. Invalid definitions do not replace the current portfolio. The saved scenario and full replay also retain portfolio settings, and results JSON includes the exact overlap report and sampled settlement.

## Offline market and disagreement diagnostics

Advanced contains **Market & research audit**. It starts without odds: the audit attachment's historical price table lacked an exact capture timestamp and redistribution permission, so it is not installed as a market fixture. Importing odds, sorting comparisons, hiding shortlist markers or reviewing annotations does not change model strengths, model probabilities, the random seed, ticket selections or the sampled race. There is no automatic market/model blend, external price fetch, bookmaker connection or betting action.

**Import an offline market snapshot** supports manual decimal odds, CSV quotes plus metadata, or a complete JSON document. Manual and CSV metadata require the provider, original HTTP(S) source URL, actual observation time including seconds and a known timezone offset, currency, market type and completeness declaration. Do not fill an unknown capture time with the current clock. A JSON snapshot uses `racelab-market-snapshot-v1` and may additionally retain publication/retrieval times, uncertainty/reuse notes, original field identity and content digest. Imported timestamps and source claims remain unverified.

Manual/CSV controls expose WIN and PLACE; ordered tote outcomes use the separate JSON representation with three ordered horse IDs/numbers and a declared unit stake. PLACE and tote snapshots can be retained but are not treated as WIN probability vectors. For runner CSVs, the required header is `horseId,number,decimalOdds,status`, with optional `notes`. Status is `active`, `scratched` or `withdrawn`; obtain stable IDs from the horse JSON. Each active decimal price must be finite, greater than 1 and at most 1,000,000. Duplicate identities, unknown entrants, mismatched IDs/numbers and malformed timestamps are rejected. Empty manual prices remain missing rather than receiving invented neutral odds.

A normalised WIN comparison requires every active runner, a true completeness declaration, compatible event/field identity and content, and consistent status/gate information. Current and captured drawn barriers and effective gates remain distinct. The current UI uses a 60-minute freshness policy and requires capture before the scheduled-race cutoff. Partial, stale, future, incompatible and non-WIN snapshots remain labelled as such, without a normalised comparison. Scratching or changing the accepted field invalidates an old comparison. A local timer checks diagnostic inputs and freshness; it does not fetch newer prices. Import cannot authenticate whether a provider actually published the supplied prices at the stated time.

Accepted snapshots are retained in local XDB history. **Saved market snapshots & export** selects a previous capture or prepares/copies/downloads its JSON; snapshots retain their original observation times. Source attribution and capture/review times appear next to the comparison. File operations use the SoftN host capability and have copy/paste alternatives. Sharing a snapshot still requires permission to redistribute its source data.

**Whole-field comparison** includes every active runner. It shows original-baseline and research win/top-three probabilities alongside quoted odds, normalised market WIN probabilities and research-minus-market gaps in **percentage points**. Sort by saddlecloth, either model, market or the absolute gap. The comparison baseline uses divisor 8 and the chosen scenario; the research comparator uses either the explicit pilot or current research coefficients with history off. These choices are printed beside the table and do not switch the active simulation model. A disclosure shows a common-scale bar chart with visible numeric/text series labels, plus per-runner explanations of contributions, omitted effects and uncertain evidence. The shortlist is a subjective human selection, not a calculated endorsement.

For a compatible complete WIN snapshot, raw implied probability is `q_i = 1 / decimalOdds_i`; raw total is `sum(q_i)`, overround is `sum(q_i) - 1`, and the proportional market proxy is `q_i / sum(q_i)`. Proportional removal of overround is one convention and can distort extreme prices. The proxy is not a known true or validated fair probability. A positive model-minus-market gap is a disagreement to investigate, never evidence of value or positive expected returns.

**Separate market-derived ticket approximation** uses that WIN vector as another Plackett–Luce model and calculates full-field ticket coverage, including overlap. Its top-three probabilities and ticket coverage are synthetic ordering assumptions derived from WIN quotes: they are not observed place/trifecta prices, tote dividends or an independently validated forecast. The market comparison reports **Expected monetary payout not estimable**; it does not manufacture dividends from WIN odds.

## Selection influence and blind review

**Selection and annotation influence** compares the count, mean and median research log-strength adjustment for selected and unselected runners, with rating-band and field-status summaries. In Portfolio mode, selected means the union of the ticket selections; otherwise it uses the quick selection. The comparison uses all active runners when calculating probabilities. A selected/unselected difference can flag circular confirmation risk, but does not prove deliberate manipulation, causal bias or predictive quality. Changing tickets changes grouping and coverage only, never horse strengths.

**Calculate research ablations** explicitly compares base only, trip only, recent form only, surface only and all selected research components. It reports the leading runner, ranking changes and exact ticket coverage over the complete active field. These calculations do not apply a different model or rewrite the portfolio. They test the influence of assumptions; they do not fit coefficients or establish calibration.

The separate `racelab-research-annotations-v2` records preserve analyst labels, rationales, source references, reviewer metadata, evidence cutoff, uncertainty and post-outcome-review status. Unknown original annotator/timing details remain unknown. Imported labels cannot claim verified factual status merely by passing validation. Independent reviewer disagreements stay visible and are not silently averaged. The original research sidecar and active pilot are not overwritten by annotation imports.

**Evidence display & independent review** provides display-only filters for observed fields, analyst interpretations and manual test fields in horse profiles. These filters never alter the forecast. **Start blind research review** replaces the ordinary application content with opaque runner labels and eligible structured facts; names, saddlecloths, trainer names, odds, shortlist choices, the scene and normal profiles are absent from this review screen. Replay pauses on entry. Distinctive race records can still reveal identities, so the app does not claim a guaranteed fully blind procedure.

Blank scores mean **Not scored**. Trip, recent-form and surface judgements are explicit analyst hypotheses, separate from observed facts; absent verified starts stay unknown rather than becoming zero starts. Enter a reviewer ID, the actual authored timestamp and evidence cutoff with timezone, rationale and uncertainty. Mark reviews made after seeing the outcome as post-outcome; those are ineligible for genuine pre-race validation. Save/export the review for independent comparison. **Exit blind review** restores the normal view without changing the model or field.

## Model: past performance plus random variation

Default strengths use **Racing And Sports numerical ratings retained in the pre-race snapshot**, rechecked against the currently linked **VRC analysis dated 2 November**. All 24 rating values match. The redirected current article is not proof of its earlier publication or an immutable copy of the original source. These are third-party past-performance assessments, not official handicap marks or direct probability estimates. Each runner has a structured most-recent start (date, race, distance, placing and field size), checked on 1 November against the Neds guide and TABtouch. This is shown separately from selected earlier form highlights, which can refer to previous seasons. These are not complete histories; all field, weight and rating values remain dated snapshots. At that 1 November check, no later scratching was found and Shockletz’s jockey was unresolved. Those are dated evidence notes, not a live verification guarantee. The separate 3 November official overlay now displays Harry Coffey and its checked field/scratching timestamps; it leaves the original research snapshot intact.

Conversion: `strength = 100 × exp((publishedRating − 115) / 8)`, rounded to two decimals. The scale of 8 is an illustrative assumption, not learned from historical outcomes. Changing it could materially change probabilities. Selected form notes provide context, not extra bonuses in the original baseline. An old win does not imply current superiority. The separate history snapshot includes career, Flemington, distance-bucket and going starts and placings. Its numbers are dated provider records; zero starts or a missing record is unknown rather than evidence of inability. The 1 November audit found no mismatches across 168 historical records and 24 latest-start summaries. Coverage is sparse: eight runners have no recorded Flemington start, and 16 have at most two (including those eight), with 51 starts across the whole field. Four have no soft-ground record and six have no heavy-ground record. These are evidence-coverage counts, not extra bonuses or penalties.

**Model preset & rating scale**, in Advanced, keeps the original v0.10 model as the default. **Ratings only** explicitly removes history, barrier and manual stamina/wet/style effects. The rating divisor can be 4, 6, 8, 12 or 16: smaller divisors concentrate rating-derived strengths and larger ones flatten them. Explicitly supplied strengths are preserved rather than replaced by a rating transform. **Reset to original model** returns the preset/divisor/research coefficients to the baseline defaults; other scenario choices remain explicit.

**Research what-if** is an opt-in, uncalibrated sensitivity mode. Its flat-trip, recent-form and soft-evidence coefficients start at zero. **Load illustrative pilot values** explicitly sets 0.06 / 0.04 / 0.02 and turns cautious history off to reduce reuse of related evidence. Analyst tags map uniformly to a bounded log-strength adjustment, capped at ±0.12; unknown evidence is neutral, and soft evidence gives no Heavy-ground bonus. The transformation changes derived model strengths without overwriting published ratings or raw field strengths. The pilot identity is `experimental-research-pilot-0.1`; other coefficient/divisor choices have distinct identities. The unavailable **Validated model** option remains disabled: neither the tags nor coefficients have been historically fitted or shown to improve forecasts.

Each Advanced horse profile has a **Model contributions** disclosure showing raw and transformed strength, effective gate, barrier/history/manual/research multipliers, final model weight and probability change. It distinguishes model inputs, manual assumptions, display-only metadata and missing information. Allocated kilograms, jockey, trainer and narrative highlights receive no independent fitted effect. **Research observations & conflicts** separates attributed snapshot facts, analyst interpretations, baseline use, research use, missing data and conflicts. Matching research adjustments require the same horse ID, saddlecloth, name, rating, drawn barrier and kilograms as the bundled snapshot; edited or imported records do not acquire eligibility merely by claiming verification.

The research sidecar is a separate, dated 24-runner record. It retains rather than silently resolves disagreements, including the provider's hurdle-inclusive 3,200 m totals for Trustyourinstinct, preliminary-versus-final Point Of Law weight, the then-unconfirmed Shockletz rider and differing distance statements for Hopewell Rock, Point Of Law and Shockletz. Such text is not converted into verified flat-start counts. The original baseline stays unchanged when research adjustments are off.

Complete finishing orders use exponential random keys (weighted Plackett–Luce rankings without replacement). Every active horse can win. Seeded Monte Carlo races produce empirical frequencies across the whole field, alongside exact calculations under the same model. Each batch uses a generated batch seed. Trial 0 uses that seed; subsequent trial i uses `RL6:<seed length>:<batch seed>:<i>` to initialise a separate pseudorandom stream. This recipe is reproducible; statistical independence of the streams has not been established. Active runners are placed in canonical ID order before sampling. Given the same seed, runner IDs, inputs and model version, rearranging the field rows therefore does not change a sampled finish or its aggregate counts. The animation uses the exact first sampled order with synthetic movement around it. Run & watch supplies fresh randomness; replay preserves it.

Stamina, manually entered wet preference and style start neutral; their coefficients are assumptions. In cautious history mode, changing the selected going can nevertheless affect relative strengths using the limited going records described below. With history off and neutral manual attributes, going and pace alone do not change relative outcomes. Weight has no extra numerical adjustment: the printed rating variant and its treatment of Cup weights are unclear, so another penalty risks double-counting. The supplied rating is not established here as a calibrated measure of current 3,200 m ability. For example, the VRC analysis gives Enfjaar the highest supplied rating while querying his stamina at this trip; the original baseline does not convert that contextual query into a numerical deduction. The separately labelled research mode uses explicit, reversible analyst-tag assumptions instead. The optional **Modest** barrier setting multiplies relative model weight by `exp(-0.08 * (effectiveGate-1)/(activeCount-1))`. This implies about 7.7% lower relative weight at the widest gate, not 7.7 percentage points less winning chance. Its magnitude is a subjective risk proxy, not fitted causal evidence, physical extra metres or a guarantee inside gates are preferable. **Off** disables it. VRC original/effective gate winner counts have unequal opportunities and do not establish a reliable effect size. Gate ordering also determines the visual start; animated lanes and traffic remain illustrative rather than simulated race physics.

**Cautious history adjustment** is an optional, deliberately small modelling assumption, not a measured causal effect. It compares each horse’s Flemington track and selected-going top-three rates against its own career top-three rate. To temper small samples, its career baseline is `(career top-three + 8 × 0.35) / (career starts + 8)`; each available, nonzero-start subset rate is `(subset top-three + 12 × baseline) / (subset starts + 12)`. It averages the available track and going contrasts with that baseline, multiplies the average by 0.25, clamps the exponent to −0.05 through +0.05 and exponentiates it to obtain a strength multiplier. Zero-start or missing subsets contribute no signal. The 8, 0.35, 12, 0.25 and ±0.05 are chosen safeguards, not fitted values. Distance and track-distance counts are retained as reference data, including in horse JSON, but excluded from the calculation because the provider’s distance-bucket definition has not been verified. **Off** removes this history adjustment while leaving other chosen assumptions unchanged. Track and going overlap, and data can reflect very different race quality, distances, fields and time periods; historical top-three fractions alone cannot establish how a horse will run here.

The **aggregate results** cover every active runner and separate mathematical model quantities from the finite batch:

- **Exact model win, second, third and top-three probabilities** marginalise the Plackett–Luce order probabilities. The first-place probability is `w_i / sum(w)`. Second and third probabilities sum over eligible ordered finishes; top-three probability is the sum of the three place probabilities.
- **Exact expected finishing position** is `1 + sum(w_j / (w_i + w_j))` over other active runners. The consensus display uses this expectation and also shows the simulated mean finish. It is a field summary, not the most probable complete finishing order.
- **Exact model box coverage** sums the ordered top-three probabilities covered by the selected runners. The UI also shows observed coverage and its Wilson sampling interval. Exact ordered-ticket and overlapping-ticket probabilities are also available through Portfolio Lab and in its export.
- **Simulated win/top-three frequencies, win counts and positional counts** are drawn from the current batch. New randomness can change those finite-sample values and the animated result. Increasing the number of trials reduces Monte Carlo noise; it does not change exact probabilities for unchanged inputs or correct a misspecified model.

The displayed top five exact ordered trifectas are the most likely under the model; the export includes the top ten. The most frequent observed ordered trifectas are selected after sampling and can change between batches. Their ordinary sampling intervals are not adjusted for that selection. The animated first trial is one example and need not match the most frequent trifecta or the consensus. The per-runner history comparison holds the rest of the scenario fixed and shows the exact win-share change with history enabled versus off.

The results export includes diagnostics comparing simulated frequencies with the exact model: maximum absolute differences, root-mean-square differences and probability-sum checks. These diagnose sampling and implementation behaviour. They are not errors against historical race results or evidence of real-race forecasting accuracy. The 95% Wilson intervals describe **Monte Carlo sampling error only**; they do not quantify parameter uncertainty, missing race information or model error.

All forecast quantities remain conditional on this uncalibrated model and its supplied inputs. There is no independent prospective holdout, learned sectional model, live data, jockey/trainer adjustment or weather/odds/injury feed. The limited historical checks below do not demonstrate a predictive advantage. Credible forecasting accuracy requires consistent pre-race snapshots, time-separated evaluation and calibration across sufficiently many comparable races.

## Assumption comparison and historical checks

Each completed batch also evaluates four fixed scenarios: the current assumptions, history adjustment off, barrier adjustment off, and both adjustments off. Each runner's evidence panel shows the range of exact win and top-three probabilities across those four scenarios. The export preserves the individual scenario values. A range is an **assumption comparison, not a confidence or predictive interval**. It does not cover the unvalidated rating scale, other omitted predictors, source errors or race-day changes. A zero-width range means these four settings agree; it does not mean the forecast is certain. No parameters are tuned by this comparison.

The additional **Rating-scale sensitivity** and **Good / Soft / Heavy comparison** disclosures run only after **Calculate comparisons** is pressed. They compare the leading runner and quick-box/portfolio coverage across the five divisors or three going scenarios, holding other inputs fixed. They do not select a best-fitting parameter, fetch official going, or quantify real-world predictive uncertainty. Explicit strengths stay fixed when the divisor changes.

The **Historical checks** panel reconstructs the 2024 and 2025 Melbourne Cups using ratings printed in VRC articles bearing pre-race dates and the verified winning/top-three outcomes. It includes 23 actual starters for 2024 after Athabascan's withdrawal and 24 for 2025. The original drawn gates compact after the withdrawal. A full historical finish order is not invented where only the first three are sourced.

The rating conversion stays fixed at `100 × exp((rating − 115) / 8)`, rounded to two decimals. Both a ratings-only setting and the existing modest barrier assumption are compared against equal win chances for every starter. Current horse histories and post-race ratings are not inserted into these fields. Historical history adjustments, stamina, wet preference and style effects are disabled because comparable contemporaneous evidence is unavailable. No coefficients were selected using these outcomes.

The pages were retrieved in **2026**, and immutable pre-race archived copies were not obtained. These are retrospective reconstructions, not a prospective or previously unseen holdout. Two variants of each Cup still represent only **two races**.

Mean winner-probability scores, with equal weight per race:

| Setting | Mean multiclass Brier | Mean log loss |
| --- | ---: | ---: |
| Equal chances | 0.95743 | 3.15677 |
| Frozen ratings; barrier off | 0.97045 | 3.20290 |
| Frozen ratings; modest barrier assumption | 0.96841 | 3.18162 |

Lower is better. Multiclass Brier is the sum across active runners of `(predicted win probability − winner indicator)²`; log loss uses the natural logarithm of the winner's probability. **Both model variants scored worse than equal chances on this small sample.** This does not establish how they will perform in a future race, and it provides no basis for claiming a reliable edge. The app keeps the result visible rather than modifying parameters to make these two past winners look more likely.

Version 0.8 also scores the top-three event rather than only the winner. The top-three Brier score sums `(predicted top-three probability − actual top-three indicator)²` over runners. Ordered-trifecta log loss is `−ln(probability of the actual first/second/third order)`. Unordered-set log loss sums the model probabilities of all six orders of those same three horses before taking `−ln`.

Mean top-three scores, with the same two races weighted equally:

| Setting | Top-three Brier | Ordered-trifecta log loss | Unordered-set log loss |
| --- | ---: | ---: | ---: |
| Equal chances | 2.61685 | 9.33782 | 7.54607 |
| Frozen ratings; barrier off | 2.81325 | 10.11011 | 8.32735 |
| Frozen ratings; modest barrier assumption | 2.80059 | 10.07488 | 8.29278 |

Again, lower is better, and both model variants are worse on this sample. The panel shows top-three Brier and ordered-trifecta log loss with their equal-chance comparisons; the JSON report also includes unordered-set probability/log loss and the eligible race count for each metric. Missing complete top-three outcomes are excluded from those particular metrics rather than treated as losses.

A leave-one-race-out **sample-sensitivity diagnostic** recomputes the averages after omitting each supplied Cup. It refits nothing and is not cross-validation, a confidence interval or an estimate of future accuracy. With two races, each omission leaves only one. The winner-score comparison changes sign between these individual Cups, illustrating how fragile the two-race average is; the top-three comparisons remain adverse. No result is used to tune the model.

Older years were reviewed but were not silently pooled. The complete 2023 VRC guide labels its 23 ratings **Timeform**, while the included 2024/2025 articles label their figures **Racing & Sports**; no documented equivalence between those measurement bases was obtained. For 2022, a complete contemporaneous numerical field on the comparable R&S basis was not obtained. The archive records the exclusion reasons and reviewed source URLs, without inventing missing ratings.

The expandable panel shows each race/variant, winner probability, equal-chance baseline, proper scores, probability of the actual ordered top three and source links. The bundled `assets/historical-cups.json` retains the input fields, publication/retrieval dates, withdrawals, known source inconsistencies, outcomes, provider-basis notes, excluded-year review and limitations. Results JSON includes both the historical reports and the four-scenario sensitivity report for independent review.

## Horse JSON import and results export

Use **Horse JSON** to paste text or choose a `.json` file. A field may be a JSON array or a `racelab-horses-v1` envelope containing `horses`; it must contain 3–40 horses and at least three active runners. Each horse requires a name, a distinct saddlecloth number and a drawn barrier, plus either positive strength or a rating from which the illustrative strength is derived. Active runners must have distinct drawn barriers. Optional fields include `id`, `strengthBasis`, `observations`, `evidenceNotes`, `weight`, `active`, `stamina`, `wet`, `style`, `colour`, `rating`, `form`, `lastStart`, `history`, trainer, jockey, sex, country, age, source, notes and snapshot. History records contain career and optional track, distance, track-distance and going records with `starts`, `wins`, `seconds` and `thirds`; they are checked for internal consistency. Export the current horse JSON for a complete example. Names cannot contain commas or line breaks because the field editor also uses comma-separated rows.

The pasted or uploaded input and its normalised, pretty-printed output must each fit within **100,000 UTF-8 bytes**. **Review JSON file** or **Validate & review JSON** validates the candidate and stages a before/after field comparison. The active field remains unchanged until **Approve field changes**; **Cancel changes** discards the preview. Approval rejects a preview if the field or import draft changed in the meantime. It does not independently verify the records or their source: imported evidence is labelled user supplied and unverified. Copy/paste is available where file access is unavailable. File picking and downloads use the SoftN host's file capability and may require its permission.

Structured observation rows have explicit identity, race type, source and time fields. The source package validates their shape and timing, keeps flat starts separate from hurdles, and does not infer starts, placings or sectionals from prose. Imported verification claims remain untrusted; these records are not automatically promoted into model bonuses. Missing data stays unknown. The accepted field has a content-derived snapshot ID, separate from the immutable research sidecar ID. The freshness and race-day disclosures identify each dated input, the reported track/forecast and unavailable live updates; it does not perform automatic race-day collection.

Asynchronous imports follow the latest request: an older file read cannot overwrite a later choice. Applying/resetting the field, running a batch, restoring a replay or loading a valid scenario invalidates pending file work. A file read is also discarded if the field editor or pasted JSON draft no longer matches the content present when the picker opened. These checks prevent delayed file callbacks from replacing newer work. Import errors and status are displayed within **Horse JSON**, outside its collapsed paste panel; an unrelated batch finishing does not erase an import error.

After an analysis completes, results can be copied or downloaded as **`racelab-results-v2` JSON**. The v2 export in app version 0.15.1 includes `raceDayConditions`, `fieldUpdate` and the current completed `boxSuggestions` report (or null). It explicitly records `isCalibrated:false`, `validation.status:"not_established"`, separate Monte Carlo/model-uncertainty descriptions, source snapshot IDs/times, market method/comparison status and research-audit reports. No market import changes the statistical replay inputs. The export also contains the field and supplied evidence, scenario, ticket/portfolio definitions and overlap probabilities, hypothetical payout cases and sampled settlement, model settings and contributions, accepted field/research snapshot IDs, seed recipe, model/data versions, aggregate counts, exact and simulated probabilities, expected and simulated finishing positions, sampling diagnostics, four-scenario assumption sensitivity, the historical winner/top-three scores, omission-sensitivity results and provenance limitations, effective model weights and assumptions, first animated outcome, replay code, stated limitations and review questions. Probabilities in the JSON are fractions between 0 and 1. The aggregate counts and estimates can be reviewed independently of the visual replay. A replay code contains the full horse data including history; restoring it still requires compatible app, model, track and data versions.

The source project provides `research-backtest.js`, an offline adapter for a caller-supplied `racelab-timed-benchmark-v1` dataset with complete fields, separate outcomes and timezone-qualified pre-race timestamps. It reports chronological partitions and expanding-origin availability lists for frozen ratings/barrier diagnostics against uniform probabilities. Eligible supplied WIN snapshots can add a separate market-derived PL comparator; a historical market-age policy must be explicit. Partial, future, stale or incompatible prices are excluded rather than filled in. The bundled date-only two-Cup reconstructions are not promoted into this stricter dataset, and same-day input publication is rejected rather than backdated.

The offline report adds winner/top-three proper scores, ordered and unordered first-three log loss, winner-rank diagnostics, reliability bins, subgroup counts and paired comparisons over the same eligible races. Seeded percentile intervals resample whole races, not starters; fewer than two races produces no interval. These intervals describe variation in the supplied evaluation races, not Monte Carlo error or a confidence band for the coming Cup. They do not eliminate cross-race horse/stable dependence or compensate for trying many models. Small-sample warnings are reporting safeguards, not validation thresholds.

Dataset/input/configuration hashes and a fixed experiment registry support reproduction. The adapter trains and selects nothing, supplies no additional races or prices, and cannot authenticate an uploaded timestamp, verify reuse permission or prove that a designer never saw an outcome. Its governance output keeps calibration unestablished and cannot promote a validated preset. There is no historical research-pilot fit or larger licensed holdout in this release. A trained enriched model, calibrated market comparison, live feed and authenticated out-of-time evaluation remain future work.

## Course and historical reference

The hand-shaped Flemington-inspired scene includes a straight start, first winning-post passage, anticlockwise circuit, rails, stands, stalls and original animated horses. It is not surveyed geodata. Published dimensions include a 2,312m circuit and 450m straight. The 888m first-post passage is derived from 3200−2312, not a verified start coordinate; the source's distance-to-first-turn convention differs. The geometry uses an approximate nominal 30 m turf width and a roughly 3.5 m nose-to-tail horse at its model scale. These are design approximations, not surveyed measurements; scenery and start placement are likewise stylised.

The original procedural horse assets have rounded bodies, heads and muzzles, short separate ears, round eyes, articulated upper/lower legs and a crouched jockey with a face, helmet, separate arms and white breeches. The 0.9 artwork refines the face and helmet, gives the barrel and neck a leaner profile, angles the rider’s thighs outward from hip to knee, and adds natural coat highlights, shading and material differences. Detailed mode adds rounded haunches and shoulders, small hooves, mane, bridle, reins, leather saddle, aligned jockey boots, a helmet visor, nostrils and decorative markings. Balanced mode retains the main anatomy and gallop while dropping those small embellishments for a lighter scene. Both use lightweight primitive geometry; they are not photogrammetric or biomechanical reconstructions. Generic coats, markings and silks remain illustrative and are not authenticated race-day colours. These refinements leave gait, trajectories, finish times and probabilities unchanged. No phone-frame-rate claim is inferred from these detail settings.

The 2023–2025 winner times average 200.12s. This is a loose replay-duration reference with synthetic seeded ±4s variation, not a fitted time forecast. The 2023–2025 history cards remain replay-duration references rather than a training dataset. The separate two-race Historical checks panel reports the limited retrospective diagnostic described above. Motion, lead changes, margins and lanes are illustrative choreography rather than telemetry or measured biomechanics.
